Words first

Supervisor, child run, contract, shared budget

An investigation now starts one supervisor run. The supervisor's model has a single tool, delegate: it proposes pieces of work as delegation contracts (a task ID, a role and a bounded objective). For each contract the application starts a child run: an ordinary run_agent with its own run ID, the supervisor's run ID as its parent, only its role's tool and no approvals. All children draw on one shared budget. The supervisor reads the children's answers and gives the investigation's answer.

supervisor
An agent whose model plans the work and whose only tool is delegate. Its run is the parent of every child it starts.
delegation contract
What the supervisor proposes: a task_id, a role (logs or runbooks) and an objective of at most 500 characters. The application validates it; the model cannot invent a role or attach tools.
child run
A run started for one contract: a new run ID, the supervisor's run ID as parent_id, only its role's tool, no approvals and its own small limits.
shared budget
One allowance for all children: tokens, the number of agents and the depth of delegation. A child reserves its share before it starts and settles what it used afterwards.
work item, deadline
The scheduler's unit of work and the time limit for the whole batch. Unfinished work at the deadline is cancelled; finished work is kept.
envelope, artifact version
A reply carries the request's correlation, task and artifact IDs and the next version number, so a late or misdirected reply cannot overwrite newer evidence.

The idea

The model may propose the split; the application decides what each part may do

Splitting work between agents adds three new ways to fail: a child that gets more authority than it should, children that together spend more than anyone allowed, and results that arrive late, twice or for the wrong request. None of them is fixed by a better prompt. Each is fixed by a check in the application, placed where the work is handed out or where a result comes back.

1 · A contract and a scoped child

Validate what the model proposes, and give the child only its role's tool. The contract.

2 · One shared budget

Reserve before a child starts, settle after; agents, depth and tokens. The budget.

3 · Parallel, with a deadline

Run independent work together, keep what finished, cancel the rest. The scheduler.

4 · Replies and review

Match every reply to its request; stop a review that never converges. Replies and review.

Design choice

Is a team worth it? Measure it against the single agent

A team is not free. On the same INC-001 investigation the two-agent team makes twice as many model calls as the single agent and reports more than twice the fixture tokens, because the supervisor plans and combines on top of the work. What it can buy is time: independent children can run at once. Whether that trade is worth it is a measurement, made with the Session 04 harness on the same cases, not a belief.

Contract

Validate what the supervisor proposes, then start a scoped child

The supervisor's model proposes a task ID, a role and an objective, and nothing else: the schema has no field for tools, approvals or limits. The application serialises the contract with sorted keys, so an identical contract reuses the result it already has, while a changed objective under the same task ID is refused. It maps the role to a fixed tool, refuses a child that would hold a tool its parent lacks, and builds the child's Context from the parent's with a new run ID, the parent's ID, the role's tool and no approvals. The parent's conversation is not copied.

Budget

Reserve before a child starts, settle after it ends

Two children that each check "is there enough left?" and then start can both see the same 5,000 tokens. So a child reserves its share, 1,800 fixture tokens, under a lock before it starts, and the reservation also counts it against the number of agents and the delegation depth. When the child ends, the budget is settled from what it reported using; a child that produced no run is charged the full reservation. A plan that needs more agents than allowed is refused at the start, and the supervisor reports what it has honestly.

one allowance, reserved and settled under a lock · agent_runtime/supervisor.py · lines 22–41 at lesson-06
@dataclass
class SharedBudget:
    remaining: int = 5000
    max_agents: int = 2
    max_depth: int = 1
    spawned: int = 0
    spent: int = 0
    lock: asyncio.Lock = field(default_factory=asyncio.Lock)

    async def reserve(self, tokens, depth):
        async with self.lock:
            if depth > self.max_depth or self.spawned >= self.max_agents or tokens > self.remaining:
                raise ValueError("delegation_budget")
            self.spawned += 1
            self.remaining -= tokens

    async def settle(self, reserved, used):
        async with self.lock:
            self.remaining = max(0, self.remaining + reserved - used)
            self.spent += used

Scheduler

Run independent work together, under one deadline

The scheduler takes work items with their dependencies. Before anything runs it rejects duplicate IDs, unknown dependencies and cycles. Then it launches ready items up to the concurrency limit; an item is ready when everything it depends on has completed, and blocked if any of it failed. At the deadline it keeps what finished, cancels the rest and waits for their clean-up, and reports partial. The runtime gets one small hook, execute_batch: when the supervisor runs in parallel, all its pending delegate calls go through the scheduler at once, each still through delegate's checks, and the results come back by tool-call ID.

Replies and review

Accept only the reply you asked for; stop a review that never agrees

Once work runs at the same time, replies can arrive late, twice or for another request. Each request travels in an envelope with a correlation ID, a task ID, an artifact ID and a version; a reply is accepted only if the three IDs match and its version is exactly the next one. Review between a producer and a reviewer gets a round limit: if the reviewer has not accepted by then, the review is escalated with the artifact and every review kept, and the one component that owns the report saves it.

match the request, then a review that ends · agent_runtime/coordination.py · lines 86–104 at lesson-06
def accept_reply(request, reply):
    if (reply.correlation_id, reply.task_id, reply.artifact_id) != (
        request.correlation_id, request.task_id, request.artifact_id):
        raise ValueError("mismatched_reply")
    if reply.version != request.version+1:
        raise ValueError("stale_or_unexpected_artifact")
    return reply.body


async def bounded_review(artifact, producer, reviewer, max_rounds=2):
    history = []
    for number in range(max_rounds):
        decision = await reviewer(artifact)
        history.append(decision)
        if decision["accepted"]:
            return {"status": "accepted", "artifact": artifact, "rounds": number+1, "reviews": history}
        if number+1 < max_rounds:
            artifact = await producer(artifact, decision)
    return {"status": "escalated", "artifact": artifact, "rounds": max_rounds, "reviews": history}

SAY Read Envelope and accept_reply. Correlation, task and artifact IDs must match the request, and the reply must advance the version by exactly one, so a reply for another request or a stale version cannot overwrite newer evidence. Then read bounded_review: the reviewer decides, the producer revises, and after max_rounds without acceptance the status is escalated with the artifact and review history preserved. The lab's reviewer always reports contradictory evidence, the review escalates, and the single owning component saves the report as version 1. Ask how learners would tell a genuine evidence conflict from a reviewer whose criteria keep changing. Both need explicit acceptance rules; the corrective action differs.

Explain the choice Typed envelopes and artifact versions fix coordination errors that prompt changes cannot. A finite review loop turns disagreement into an escalation with evidence.
