Concept00:10–00:18

Model, runtime, tool: three boxes, one loop

A workflow

Steps are fixed in advance by the developer.

  1. read the log
  2. search the runbook
  3. write the summary

Predictable and cheap. Keep it as your baseline.

An agent

The next permitted step is chosen from what was just observed.

  1. propose → run → observe
  2. propose → run → observe
  3. … then answer, or stop

Flexible, so it needs explicit limits and evidence.

Our default model is a deterministic mock provider. It is a scripted policy, not intelligence: it reads the log, then searches the runbook for the cause it saw, then answers from the sources it observed. Everyone gets the same behaviour with no credentials and no network variability.

OpenAI-compatible and Anthropic adapters translate real provider responses into the same internal shape. A passing offline test proves the loop and its boundaries. It does not prove model quality; that needs a separate, authorized benchmark.

Poll

A provider hangs and returns nothing. Which component stops the run?

Show the answer

The runtime, with its elapsed-time limit. No step or token is consumed while a call hangs, and an instruction to the model cannot enforce a deadline.

Concept00:24–00:30

The application owns identity and limits. The model owns nothing.

FieldOwnerWhy it matters
tenant, run_id, roleapplicationA retrieved document must never be able to switch tenant or identity.
allowed toolsapplicationPermissions are granted by code, never claimed in model output.
Limits: steps, tokens, seconds, output sizeapplicationEach limit catches a different failure; together they bound every run.
messages, proposed tool calls, the answermodelUntrusted input. The runtime validates it before acting on it.
eventsruntimeWhat happened, step by step. From Session 08 the console shows it as a run timeline.
step_budgetdefault 8 model steps

Stops a loop that never converges.

token_budgetdefault 8,000, checked before each call

Reserves room for the reply before dispatch, then rechecks reported usage.

TimeoutErrordefault 20 s for the whole run

Catches a hang that consumes no steps and no tokens.

repeated_actionsame tool, same arguments, same run

Stops an agent stuck asking the same question.

Every stop is a named, explained outcome, never an unexplained exception.

reference · incident/core.py · lesson-01 · inside run_agent()
while run.pending:
    call = run.pending[0]
    key = json.dumps([call["name"], call["args"]], sort_keys=True)
    if key in seen:
        raise ValueError("repeated_action")
    seen.add(key)
    result = await execute(call["name"], call["args"], run.context)
    run.messages.append({"role": "tool", "tool_call_id": call["id"],
                         "content": json.dumps(result)})
    run.pending.pop(0)
    save()
Ask

What goes wrong if we append a tool result without its assistant tool call?

Show the answer

The conversation is no longer a valid request and result pair; providers may reject it, and we lose the evidence needed to explain the run. Saving pending calls before execution is also what lets a run pause and resume later.

Expect: INC-001 answers connection_pool_exhaustion citing log-acme-001 and rb-pool-v1 after 3 model steps; the repeating provider stops with repeated_action.

The token check, in one sentence. Before each model call the runtime estimates input as characters ÷ 3, adds the maximum reply size, and refuses the call if that would exceed the budget. It is a reservation, not a tokenizer count, and reported usage is checked again after the reply.

Cost. Cost is computed only from prices you configure. A zero means "no prices configured", not "free".

Close01:55–02:00

You own the loop every later agent will use

An agent is a loopthe model proposes, the runtime decides and executes, the tool observes.
Authority is codetenant, role and permitted tools are set by the application, never by model output.
Every run is boundedand every stop has a name and a reason.
Completed is not solvedlook for cited evidence or an honest "insufficient evidence".
