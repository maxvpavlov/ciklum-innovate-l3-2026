Why agent teams

Single agents are everyday tools. Enterprise work needs agents that work together.

An agent that reasons, calls a tool, reads the result and decides what to do next is no longer news. Today we still build that loop from scratch, because everything later stands on it. If you already know ReAct, treat today as a solid foundation that you will keep extending, not as the point of the course.

Many enterprise tasks are too big, too varied or too sensitive for one agent. Coding agents already show the pattern: to implement a large feature, an orchestrator plans the work and leads subagents, each with its own task and its own context, then reviews and combines what they return.

When to split the work

When do you need more than one agent?

The work outgrows one context

The projected work will not fit in one agent's context window. Compacting the history step by step does not help either, because the work splits naturally into parallel parts and each part needs its own isolated context.

supervisor and subagents
The work is better done in a clean context

Even when everything would fit, a sub-task often goes better in its own fresh context. The agent sees only what that task needs, without unrelated history, other branches of the work or earlier mistakes pulling its attention.

scoped subagents
Each sub-task needs a different model

A strong model plans and judges, while faster, cheaper models handle routine sub-tasks. Switching models per sub-task changes quality, cost and latency.

model routing
Access must be isolated

An agent is bound to one external system or service, or acts for one particular person, and must see only that system's data and that person's permissions.

A2A · gateway · identity

If none of these applies, one agent is the right design. Adding agents adds cost, latency and failure modes, so each one has to earn its place.

Why a platform

A platform is the natural next step for agentic applications

Once you run many agents, something has to spawn them, configure them, host them and give everyone one place to manage what they do. That is the agentic platform: the central hub for agentic operations. It also adds the traceability and control points that a single agent cannot provide on its own.

Who called what?

Every tool call passes one policy check and lands in one audit record.

tool gateway · policy · audit
On whose behalf?

Each agent acts for a known person, with narrow, short-lived credentials and recorded approvals.

identity · delegation · approvals
When does it stop?

Every run has step, token and time limits, so loops cannot run away.

bounded runtime · budgets
Is version 2 better?

Changes ship on measured quality, cost and latency, not on a good feeling.

evaluation · release gates
How do agents work together?

A supervisor delegates inside the platform, and A2A reaches agents run by other teams.

orchestration · A2A
What actually happened?

Operators see which agent version ran, every decision and every failure, not just the final answer.

traces · registry · console

This course is about building those control points. You leave with a working sandbox platform you built and can explain, and with the judgement to tell which parts a real project needs.

The premise

The platform we build investigates incidents

To keep twelve sessions concrete we use one invented domain throughout: an incident-investigation platform for two fictional companies, Astro and Locomotive. Agents read logs and runbooks, explain what went wrong with cited evidence, and may propose a remediation that a human must approve.

Picture how it starts. At Astro, the payments team notices that checkout has become slow and reports it to the service desk, which opens a ticket. On our platform an investigation agent picks the ticket up. It cannot change anything. It can only read, using two tools, and it must answer with a cause and the evidence for it.

It is a good teaching case because it needs everything a real platform needs: tools, evidence, tenants that must not see each other's data, approvals before any effect, and more than one agent. All data are synthetic, and no real system is ever touched.

Ticket

The report from the business: which service, what people noticed, and an ID such as INC-001. It is the agent's task.

Log record

What the monitoring system captured for the incident. The log_lookup tool returns it: the service, the signal (for example, a 900 ms database wait after a deployment) and a suspected cause.

Runbook

A team's written procedure for a known kind of failure: how to recognise it, what usually causes it, and what an operator should do. It is a document for people, not a script. The runbook_search tool finds matching entries, and the agent reads them as evidence. It never runs them.

In our data a runbook is a short entry. For example, rb-pool-v1 describes "payments connection pool exhaustion, DB wait after deployment" and suggests "consider rollback after approval". That suggestion is only text. Doing it would be an effect on a real system, so the platform will require a human approval first.

Today's build: the runtime

The ReAct loop: reason, act, observe

Today we build only the centre box of the platform. Every later capability, including subagents, remote agents, the gateway and identity, reuses this loop.

ReAct (reasoning and acting) describes an agent as a repeating cycle: a thought about what to do next, an action, and an observation of the result, until the agent can answer. With today's native tool calling the cycle maps directly onto the API. The model's turn may contain its reasoning and a request to call a tool; the runtime runs the tool; the result goes back to the model as an observation.

What the model can send back

Every call to the model returns one assistant turn, and the provider also reports why the turn ended. The runtime decides what happens next from that structure, never from the wording.

The turn containsWhy it ended (OpenAI / Anthropic)What the runtime does
One or more tool calls, often with some text before themtool_calls / tool_useRuns the permitted calls, appends each observation with the same call ID, and calls the model again.
Text onlystop / end_turnThe model considers itself done, so this is a candidate final answer. The runtime checks it against the answer contract: the required shape, and citations that were actually observed.
Text that was cut offlength / max_tokensNot an answer. Stop with a named reason, or continue with a larger budget.
A refusal or filtered outputcontent_filter / refusalNot an answer. Stop with a named reason.

Where the thought goes. Reasoning appears either as visible text in the turn, often just before a tool call ("the log shows a pool wait, so I will search the runbooks"), or as separate reasoning the provider produces: hidden reasoning tokens in OpenAI's reasoning models, or thinking blocks in Anthropic's extended thinking, which must be sent back unchanged during a tool loop. Either way, reasoning is never an action and never evidence. The runtime acts only on tool calls and accepts only an answer that passes its checks, which is why the event log records actions and usage, not thoughts.

Text that is not the answer. A model can reply with text and no tool call that is not a final answer, such as "let me check the logs next". With native tool calling, a turn without a tool call ends the loop, so the runtime must decide explicitly: accept it as the answer, reject it with a named reason, or ask the model to continue or to answer in the required format, counting that as another step. It must never guess.

Our first runtime handles the first two rows: a turn with tool calls means act, anything else must be the final JSON answer. A cut-off or refused reply, non-final text or an answer wrapped in extra formatting fails without a named reason. The mock model never produces those cases; we harden the runtime for them when we switch to a real model.

Why an agent, not a hard-coded sequence

An AI investigation platform is worth building only where incidents are too varied and too entangled to follow a path written in advance. The next step depends on what the last one revealed, the evidence is spread across systems, and the investigation should end in a fix that a person approves. An agent orchestrates that: it chooses each next step from what it has observed, within limits the platform enforces.

Our sandbox tickets are deliberately small, so you can watch every step. INC-001 alone could be a hard-coded sequence. The loop matters as soon as cases differ: INC-002 needs a different runbook question once the log is read, and INC-003 should end with an honest "not enough evidence". Real incidents chain many more such decisions, and later sessions add the parts that handle them: subagents, remote specialists and approved fixes.

A hard-coded sequence

The developer fixes every step in advance.

  1. read the log
  2. search the runbook
  3. write the summary

Predictable, but it breaks on the first case that does not follow the script.

An agent-driven investigation

The next permitted step is chosen from what was just observed.

  1. propose → run → observe
  2. propose → run → observe
  3. … then answer, or stop

Adapts to each case, so it needs explicit limits, cited evidence and approval before any fix.

Every change you make is measured against a baseline on the same cases, starting with this single agent.

Our default model is a deterministic mock provider. It is a scripted policy, not intelligence: it reads the log, then searches the runbook for the cause it saw, then answers from the sources it observed. Everyone gets the same behaviour with no credentials and no network variability.

OpenAI-compatible and Anthropic adapters translate real provider responses into the same internal shape. A passing offline test proves the loop and its boundaries. It does not prove model quality; that needs a separate, authorized benchmark.

Ownership and limits

The platform sets identity and limits. The runtime enforces them. The model owns nothing.

FieldSet byWhy it matters
tenant, run_id, roleplatformA retrieved document must never be able to switch tenant or identity.

Limits: steps, tokens, seconds, output sizeplatformEach limit catches a different failure; the runtime enforces them, and together they bound every run.

Platform, runtime, model. The platform sets who a run is for, what it may use and how far it may go. Until Session 08 the code that starts a run plays the platform: today the lab or a test calling run_agent; from Session 08 it is Platform.submit, which takes the tenant and role from the signed-in user and the permitted tools from the agent's registry definition. The runtime, core.py, enforces the limits, validates what the model sends and records events. The model only proposes. Where the prompts say "application-owned", they mean set by the platform side, never by the model.

step_budgetdefault 8 model steps

Stops a loop that never converges.

token_budgetdefault 8,000, checked before each call

Reserves room for the reply before dispatch, then rechecks reported usage.

TimeoutErrordefault 20 s for the whole run

Catches a hang that consumes no steps and no tokens.

repeated_actionsame tool, same arguments, same run

Stops an agent stuck asking the same question.

Every stop is a named, explained outcome, never an unexplained exception.

core.py is the agent runtime: the core of every agent you will run. It holds the data the platform sets (who is asking, what is allowed, the limits), the shape of a model's reply and of a run, and the ReAct loop. From Session 08 the platform hosts it: it chooses which agent version runs, queues and limits the run, gives it an identity, and records what happened. A supervisor agent built from this same loop coordinates other agents from Session 06.

Step 1 creates it with the data contracts only. Step 3 adds the loop to the same file. The given files are data and a scripted mock model that everyone shares, so every learner gets the same results; they are not what this session teaches.

The platform and its agents are separate concerns. In production, agents run in their own processes or sandboxed containers, apart from the platform's control plane, so a misbehaving agent cannot reach the platform's data or secrets. In this course the platform runs agents in its own process, a compromise that keeps everything runnable on a laptop while you learn the concepts; the remote specialist in Session 07 shows the separate-process version.

  • Parse. The turn's text must be bare JSON. or "{}" turns an empty reply into an empty object, which then fails the next check with a named reason. Text that is not JSON at all, such as prose or JSON inside a code fence, fails here without a named reason: the gap noted in "What the model can send back".
  • Shape. The answer must have all four fields the system prompt asks for: status, cause, summary and evidence. Otherwise the run fails with invalid_final_answer. Their values are not checked yet.
  • Evidence. All tool results in the conversation are joined into one text, and every source the answer cites must appear in it. An invented source fails the run with unobserved_citation. An empty list passes, which is right for an honest insufficient_evidence answer.
  • Accept. Only then is the answer stored, the run marked completed and saved.

Later this check moves into security.validate_answer and gets stricter: status must be complete or insufficient_evidence, cause and summary must be text, evidence a short list of strings, and each citation must equal a source ID a tool actually returned, not just appear somewhere in the text.
