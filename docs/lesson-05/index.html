Checkpoints, recovery and human approvalA run that stops can continue: after a crash, and after a person decides

Until now a run lived only in the memory of the process running it. If the process died, the run was gone, and a write it had already made could be made again on the retry. Today the run's state is saved at every boundary, a write waits for a person's decision on the exact action, and a resumed run uses saved evidence, not a guess, to tell what has already happened.

Words first

Investigation, run, step, worker: what each word means today

An investigation is the question someone asks the platform: what caused INC-001 for Astro? A run is one agent's attempt at one task, with its own run ID, tenant, status and history. Submitting an investigation starts a run to answer it; submitting the same investigation again starts another run. The two are not always one to one: from Session 06 one investigation is answered by a supervisor's run and its child runs, and a run need not be an investigation at all, since this lesson's demonstration run carries out a remediation. Inside a run the agent takes steps, one model call each, and a worker is the process that executes the run. Until today one worker took every run from start to end; today a run starts to outlive its worker.

Design choice

Who owns the run: the platform, or the agent runtime?

Before building durable runs, decide where they live. In the first design the platform owns the runs: it keeps every run in its own store, and the agent runtime is a library a worker calls when there is work to do. Sessions are managed in one place, an approval is a stored decision plus a resume, and a runtime is created on demand and dropped when the run pauses. In the second design each agent runtime is an independent service that owns its sessions, for example one instance per client or per vendor agent. It isolates better and scales on its own, but the platform no longer holds the state it has to coordinate, and an approval turns into a state-management exercise between two systems.

It is the same choice SaaS made about tenants: one shared deployment where tenants are rows in a common database, or a dedicated instance for a premium client. Neither is wrong; they cost different things.

The idea

A run must be able to stop and continue without guessing what already happened

A run stops for two reasons. Sometimes it means to: a write needs a person's approval, and nobody should keep a process waiting for a human. Sometimes it does not: the worker crashes, is redeployed or loses its machine. Either way the run must continue later in another process, which knows nothing except what was saved. Recovery is only as good as the records it reads, so the question for every boundary is: if the process dies exactly here, what is saved, and what will the resumed run do?

SAY An agent can fail after deciding what to do, during a tool call or after an external effect has happened. A restart must distinguish those situations. Today we persist the same runtime state and demonstrate a deliberately difficult boundary: a worker disappears after a mock write but before it records the tool result. We will restart the executor, resume the run and prove that the effect ledger still contains one action. This lesson is about explicit ownership and recovery semantics, not merely saving a chat transcript.

Snapshot

Save the whole run, and save the call before you make it

A snapshot is the run as plain data: everything a new process needs to continue, and nothing it has to guess. The order of saving matters as much as the content. The loop records the model's tool calls as pending and saves the run before executing them, so a crash at any later moment still leaves the call on record. When the tool boundary raises ApprovalRequired, the loop does not fail: it stops with status waiting_approval, keeps the call pending and saves.

Approval

A person approves one exact action, for a limited time

The decision is a record of its own, not a field on the run. It names the tenant, the run, the action key of the pending call, an expiry and the verdict, approve or deny. The action key binds tenant, run, tool and canonical arguments, so approving a rollback of INC-001 says nothing about a rollback of INC-002. A denial ends the run as denied. The proposal comes from RemediationProvider, a clearly labelled fixture that always proposes the same rollback: a way to reach the approval branch, not an operational recommendation.

def decide(self, tenant, run_id, decision="approve", ttl=300):
    if decision not in {"approve", "deny"}:
        raise ValueError("invalid_decision")
    run = self.load(tenant, run_id)
    if run.status != "waiting_approval" or not run.pending:
        raise ValueError("no_pending_approval")
    call = run.pending[0]
    key = action_key(call["name"], call["args"], run.context)
    self.db.execute("INSERT OR REPLACE INTO approvals VALUES (?,?,?,?,?)",
                    (tenant, run_id, key, time.time()+ttl, decision))
    if decision == "deny":
        run.status = "denied"; self.save(run)
    return {"key": key, "name": call["name"], "args": call["args"], "decision": decision}

Decide only what is pending. A run that is not waiting, or has no pending call, gets no_pending_approval: there is nothing to approve.

The person, not the agent, decides. When you prepare the demonstration, your coding agent shows the proposal and stops. Approving on your behalf would turn the control into a formality.

Expiry is part of the decision. An approval given a minute ago for a five-minute window is valid; the same approval an hour later is not, and the run keeps waiting.

Resume

Continue the same loop from the saved pending call

Resuming is not a new kind of execution. resume_run loads the snapshot, refuses a run that was denied or cancelled, replaces the run's approved keys with the ones whose decisions are still valid, and hands the run to the same run_agent with initial=run. The loop sees a pending call and executes it before it asks the model anything. If the approval expired, the boundary raises ApprovalRequired again and the run is back to waiting_approval: authority is never renewed silently.

async def resume_run(store, tenant, run_id, provider, tools):
    run = store.load(tenant, run_id)
    if run.status == "completed":
        return run
    if run.status in {"denied", "cancelled"}:
        raise PermissionError("terminal_run")

    task = next(m["content"] for m in run.messages if m["role"] == "user")

Ask yourselfAsk the room

What evidence distinguishes a safe retry from an unknown remote effect?

Show the answer

A durable receiver-side result for the same idempotency key. Without it, recovery must reconcile the external state before proceeding.

Ask yourselfAsk the room

After crash B the run is resumed and finishes. Before that, what status did the saved run show, and does it matter?

Show the answer

Still waiting_approval: the loop sets running in memory when it resumes, but the next save comes only after the observation, which the crash prevented. The checks do not mind, because resume reads the pending call and the ledger, not the status. A console would show a run as waiting whose write has already happened, so a platform that shows status to people saves running before dispatching a resumed call.

Ask yourselfAsk the room

Why does WorkerCrash derive from BaseException, not Exception?

Show the answer

A real process loss is not an error the loop can handle: it simply stops. Code that catches Exception, such as a retry or a failure handler, would otherwise turn the simulated crash into a recorded failure and save it, which a dead process could never do.
