This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this workspace is

Authoring workspace for the Ciklum internal course **Innovate: Building Agentic Platforms** (L3, 2026): 12 sessions, 20 contact hours. Learners build a sandboxed *incident-investigation* agent platform step by step: an agent runtime first (01–07), then the platform around it — agent registry and platform console (08), MCP tool gateway (09), agent identity and delegated credentials (10), operations and releases (11). They do it by prompting their own coding agent, not by typing commands. The work here is mostly course design and content; the code is a teaching reference.

## incident-platform: commands

Run everything from `L3 2026 Agentic Platform Instructor Materials/incident-platform/` (quote the path because it contains spaces). Pinned deps are in `uv.lock`. The course materials and the Dockerfile target Python 3.12, but `pyproject.toml` allows `>=3.12,<3.15` and there is no `.python-version`, so pass `--python 3.12` or uv may choose 3.14.

```bash
uv sync --python 3.12                                # create .venv (gitignored)
uv run python -m pytest -q                           # full suite: 51 tests, ~20s, fully offline
uv run python -m pytest -q tests/test_lesson05.py    # one lesson's tests
uv run python -m pytest -q tests/test_lesson05.py -k approval   # one test
uv run python -m incident.lab 8                      # run a lesson demo (1..LESSON), prints JSON
uv run python -m incident.evaluate --trials 3 --split held_out  # writes var/evaluation.json
uv run uvicorn incident.api:app --port 8000          # platform API; console at http://127.0.0.1:8000/console/
A2A_BASE_URL=http://127.0.0.1:8010 uv run uvicorn incident.a2a_service:app --port 8010  # remote specialist
A2A_URL=http://127.0.0.1:8010 uv run uvicorn incident.api:app   # API that registers/pins the specialist at startup
uv run python -m incident.client submit INC-001 --agent team --wait   # CLI client (PLATFORM_TOKEN, default demo-astro)
docker compose up --build                            # restricted container: read-only, no egress, tmpfs state
```

- **Run `python -m pytest`, not bare `pytest`.** `pyproject.toml` has no `[build-system]`, so uv never installs the `incident` package. Bare `pytest` fails every file with `ModuleNotFoundError: No module named 'incident'`; `python -m` puts the cwd on `sys.path`.
- There is no linter or formatter config.
- Labs 11 and 12 write `var/trace.html` and `var/capstone-comparison.json` relative to the cwd. Labs 7 and 11 (and a lesson-10 test) start a uvicorn subprocess on an ephemeral loopback port (`incident/local_service.py`) and clean it up themselves. From lesson 09 the gateway keeps MCP stdio subprocesses open; code that builds a `Platform` should `await platform.close()`.
- The console (`incident/console/`) is vanilla ES modules with no build step and no external assets (it must work in the no-egress container). To look at it, start the API and drive it with the preinstalled Playwright/Chromium; sign in with `demo-astro`, `demo-operator` or `demo-locomotive`.

## incident-platform: checkpoint model

- Git tags `lesson-00` … `lesson-12` mark the end state of each session. `course-complete` sits on top; the commits after it change only `README.md` and `LEARNER_PROMPTS.md`. Each lesson adds one module/lab plus `tests/test_lessonNN.py`.
- `incident/__init__.py` sets `LESSON = N`. `incident.lab` refuses any lesson above it, and learners raise it only when the capability is verified.
- `TESTING.md` records the expected passing-test count per tag (1, 7, 10, 13, 15, 17, 25, 27, 33, 37, 43, 48, 51). To check a checkpoint in isolation, unpack it the way the reference was verified: `git archive lesson-05 | tar -x -C <tmpdir>`, then run the suite there.
- **Treat the reference as frozen unless the user explicitly wants to change it.** A code change in lesson N has to reach the `lesson-N` tag and every later tag (they sit on the standalone line, so this means rebuilding that line and re-tagging), plus the guide excerpts (see "Guide–repo coupling" below). It also has to reach the numbers quoted in README, TESTING and the guides: the 51 tests, and a capstone mean usage drop from 75 to 63 (16%). Rebuild the guides with `guide-builder` and run its `check.py` after any re-tag.

## incident-platform: architecture

Everything is built on one loop, `core.run_agent(provider, execute, schemas, task, context, limits, …)`:

- **Provider protocol:** `async complete(messages, tools, max_tokens) -> Reply(message, tokens, cost_usd)`. Messages and tool schemas use OpenAI chat format internally. `HTTPProvider` converts to Anthropic Messages when `kind="anthropic"`. `provider_from_env()` returns `MockProvider` unless `MODEL_PROVIDER` is set.
- **Executor protocol:** `async execute(name, args, context) -> dict`. A supervisor's `delegate` tool and the tool executor both plug into this same slot.
- **Loop behavior:** pending tool calls are saved via the `checkpoint` callback *before* dispatch, and `ApprovalRequired` pauses the run as `waiting_approval`. Guards fail the run with a code: `step_budget`, `token_budget`, `TimeoutError`, `repeated_action`. The token budget is checked before the call using `len(json)//3` plus `max_output_tokens`. The final JSON answer goes through `security.validate_answer`, which rejects citations of source IDs that were never observed.
- **`Context` is application-owned identity:** tenant, role, allowed tools, approved action keys, parent_id and (from lesson 10) the delegating `subject`. The model never controls it; child runs get a narrowed copy through `dataclasses.replace`.

The layers on top, in lesson order:

- **Tools (`tools.py`).** `ToolExecutor` handles authorization (`context.allowed`), jsonschema validation, output-size limits and one retry. Reads go through a pluggable `read_handler`, which evolves from `fixtures.simple_tools` to `context.context_tools` (ranked retrieval) to `mcp_bridge.MCPReadAdapter`. The MCP adapter talks to a real MCP stdio subprocess, and the launcher binds the tenant via `INCIDENT_TENANT`. The only write tool is `mock_remediate`. It requires `action_key` (sha256 of tenant, run_id, name, args) in `context.approved`, and it records the effect in an SQLite `effects` ledger within the same transaction, so a replay after a crash is idempotent.
- **Context and durability.** `context.py` handles message selection that never orphans tool-call IDs, the versioned artifact store (optimistic `expected_version`) and TTL memory. `durable.py` provides `RunStore`, with `runs`, `approvals` and `leases` tables, and `resume_run`.
- **Multi-agent.** `supervisor.Supervisor` runs its own `run_agent` with a single `delegate` tool. Each child is another `run_agent` with a narrowed Context, all under a lock-guarded `SharedBudget` (tokens, max agents, depth). Parallel delegation goes through `coordination.schedule`, a dependency-aware scheduler with a deadline. `platform.HybridSupervisor` sends the `runbooks` role to the remote A2A specialist (`a2a_service.py` server, `a2a_client.RemoteSpecialist`), using bearer auth, streaming and cancellation. From lesson 10 the specialist accepts only an audience-bound delegated token (`agent:runbook-specialist`) and takes the tenant and subject from its claims.
- **Registry (`registry.py`, lesson 08).** Schema-validated, immutable, versioned agent definitions (`single`, `team`, `remediator` seeded at v1) with a content hash, `activate`/`retire` (a retired version cannot run), `discover(skill)`, remote A2A agents pinned by Agent Card hash (`register_remote`; a changed card is refused, and the runtime re-checks the pin), and from lesson 09 tool servers with manifests, pinned tool definitions and a `catalog()`.
- **Platform (`platform.py`).** `Platform.submit` resolves the definition from the registry, records the exact version and hash in the run, and queues it; a worker then goes through `operations.Admission` (queue and rate limits, lesson 11), a lease and a semaphore. It dispatches by `spec.kind`; `team` uses Supervisor workers, plus the A2A specialist when the registry has a remote agent with the `runbooks` skill (`await platform.register_remote_agent(url)`). All stores share one SQLite file (`var/platform.db`, or `PLATFORM_DB`).
- **Tool gateway (`gateway.py`, lesson 09).** Every tool call from single agents, workers and the remediator goes through `ToolGateway.execute`: policy (`unknown_tool`, `not_granted`, `tenant_not_served`, `tool_definition_changed`, `write_role_required`, `argument_policy`, then the credential check, then `tool_call_budget`), an audit ledger (`gateway_audit`, args stored as a hash), and the wrapped `ToolExecutor` for validation, approval and effects. Upstream MCP sessions are shared per (server, tenant); each is opened and closed by its own owner task (anyio cancel scopes must exit in the task that entered them). Tool definitions are pinned on first connection; a later difference quarantines the server.
- **Identity (`identity.py`, lesson 10).** `TokenIssuer` makes HMAC-signed JWT-shaped tokens (iss/aud/exp checked); `Delegation` mints a per-execution token for each run (`sub` user, `act` agent), narrower child and remote tokens that extend the `act` chain, keeps tokens in memory only (never in run state), records grants, and revokes a run's tree when it ends. `CredentialStore` releases `secret://` references to named consumers with an audit trail and returns `Secret` objects that refuse to print or serialize; it holds the signing key and, if set, the model key. Registry definitions may reference credentials only as `secret://` refs.
- **API and console.** `api.py` is FastAPI. Demo credentials `demo-astro` (analyst), `demo-operator`, `demo-locomotive` (overridable via `PLATFORM_IDENTITIES`) are accepted directly and, from lesson 10, exchanged at `POST /auth/token` for one-hour signed tokens (the console keeps only the token). Only operators may decide approvals, and a decision must echo the current proposal key. Endpoints: runs lifecycle, `/registry`, `/platform` (the platform map from `blueprint.py`, with built/planned status from `LESSON`), `/gateway`, `/identity`, `/runs/{id}/trace`, `/operations`, and the console at `/console` (strict CSP; scripts must never render data as HTML — a test forbids `innerHTML` and friends). **All route handlers must be `async def`:** workers and handlers share one SQLite connection per store, and a sync handler would run in the threadpool and corrupt it (a test enforces this).
- **Ops.** `operations.py` provides traces built from parent/child runs, `release_gate` (which requires the same `dataset_sha256` and split), `evaluate_platform` and the `ReleaseLog` shown in the console. `tuning.py` contains the capstone experiments: `EfficientMockProvider`, the tenant/config-partitioned `CachedProvider` and `RoutingProvider`.
- **Labs.** `incident/labs/lNN.py` each expose `async demo()`. It asserts the lesson's guarantees and returns a JSON-able dict, and most `test_lessonNN.py` files simply call it.

Fixture facts that other material depends on:

- All data are synthetic (`fixtures.py`). Tenants are `astro` (INC-001 pool exhaustion, INC-002 clock skew, INC-003 unknown) and `locomotive` (INC-001 quota exhaustion).
- `evaluate.CASES` holds 5 cases split into `development` and `held_out`. Their hash is the dataset identity, so editing cases breaks comparability.
- Mock providers are deterministic policies, and the "tokens" they report (20 per tool call, 35 per answer) are teaching metrics, not tokenizer counts or cost. Changing them silently changes the published capstone numbers.

Configuration comes from environment variables only; no `.env` file is loaded:

| Area | Variables |
|---|---|
| Model provider | `MODEL_PROVIDER` (`mock` \| `openai` \| `openai-compatible` \| `anthropic`), `MODEL_NAME`, `MODEL_API_KEY`, `MODEL_BASE_URL`, `MODEL_ALLOWED_HOSTS` |
| Pricing | `MODEL_INPUT_USD_PER_MILLION`, `MODEL_OUTPUT_USD_PER_MILLION` |
| A2A | `A2A_URL`, `A2A_BASE_URL`, `A2A_ALLOWED_HOSTS` (the static `A2A_TOKEN` was removed in lesson 10) |
| Platform | `PLATFORM_DB`, `PLATFORM_IDENTITIES`, `PLATFORM_SIGNING_KEY` (defaults to a dev-only key; the specialist must share it), `PLATFORM_TOKEN` (client) |

The live adapters were tested only against mock HTTP. Default to `mock`, and never run a paid call without explicit authorization.

## Course content conventions

- **Learners drive their own coding agents.** Learner-facing material gives *prompts*, not terminal command snippets, as stated in the README. The executable CLIs, labs and tests exist for the coding agents to use.
- **`LEARNER_PROMPTS.md` follows a fixed shape per lesson.** Each lesson has a kit/answer-key line, then `Prepare the workspace`, `Add the check pack`, `Build step 1–4`, `Learner exercise`, `Verify the checkpoint`, `Review the result`, and several `Recover when …` troubleshooting prompts. Keep new or edited lessons in this shape.
- **Learners build from the kit, not the reference.** They build in their own repository in the course GitLab group from the learner kit (`learner-kit/` at the repository root). The repository is public, so the reference is visible too; the prompts ask the agent not to use it, and the check packs, not the code, prove the learning. `guide-builder/kit.py` generates it from the tags: `starter/` (lesson-00) and per lesson `given/` (fixtures, mock providers, `CASES`, the service launcher) and `checks/` (labs and cumulative tests), plus the interfaces the checks import. Run `kit.py --verify` after any re-tag; edit the `GIVEN` list there to change what is given. Session 01 is an instructor demonstration; learners repeat its prompts after class.
- **Terminology: never call a fixed-step program a "workflow".** Say "hard-coded sequence" (as opposed to an agent-driven investigation). In platform engineering "workflow" means a business process, so keep the word for that, and for GitHub Actions workflows.
- **Recurring teaching stances to preserve:**
  - A coding agent's completion message is not evidence.
  - Unrun or skipped checks are not passes.
  - Report failures honestly.
  - Fixture metrics are not live-model or cost claims.
  - Local guarantees such as idempotent effects do not automatically extend to external APIs.
  - Never alter expected outcomes to get a pass.
- **Instructor guides share one template and are generated.** Edit `guide-builder/specs/NN.json` (lesson content) or `specs/_common.json` (shared boilerplate), then run `build.py` and `check.py` (see `guide-builder/README.md`); never edit the generated .docx or .md files by hand. Each guide is about 3.5–4k words:
  - Header: outcome, duration, and starting/ending checkpoint with the tag hash.
  - "Where this session sits in the platform": a paragraph plus a 12-row component table.
  - Preparation, which holds two setup prompts plus readiness, offline-fallback and pinned-version notes.
  - Timed agenda table.
  - Instructor script: four build steps, each written as SAY → SHOW → PROMPT → REVIEW → "Explain the choice" → ASK/"Likely answer" → PAUSE.
  - Learner practice: exercise, VERIFY and expected JSON. Guides 08–12 embed console screenshots with "CONSOLE" captions.
  - Completion criteria, including the recorded test count and the files changed.
  - Demo troubleshooting, verification scope, session close, and references.
- **Guide–repo coupling is exact and checked by `guide-builder/check.py`.** Every guide has 13 prompts and 4 code excerpts.
  - Each REVIEW excerpt cites "source lines X to Y at lesson-NN" and matches that tag exactly.
  - Each "Files changed" list equals `git diff lesson-(N-1)..lesson-N`.
  - Expected JSON matches the lab output (run ids and timings vary).
  - All 156 prompts appear verbatim in `LEARNER_PROMPTS.md`.

  Keep all four in sync when editing any of them.
