The idea

An agent decides well only from a well-kept request

The model makes every decision from what is in the request it receives: the instruction, the task, the conversation so far and the evidence its tools returned. Too little and it guesses; too much, stale or another tenant's, and it is misled or leaks. So before each request goes to the model, the platform keeps it in order. Today you build that housekeeping in three places, then send the same well-kept request to a real model.

1 · What the agent can find

Its tools return only the run's tenant's runbooks, ranked, each with a source ID it can cite. Filter by tenant first, then rank.

2 · What the next request carries

The instruction, the task and the newest complete rounds that fit a budget; the full history is kept aside. Trim by complete rounds.

3 · What outlives the request

Reports saved as versioned artifacts, and small facts remembered until they expire. Artifacts and memory.

4 · Who reads the request

Where we are

Yesterday the platform decided what a tool may do. Today it decides what the model gets to read.

A larger context window does not decide which information is relevant, current or authorized. Your agent already has a loop and a tool boundary; today we control the evidence that flows through them. In the payments incident there are four kinds of it, and each lives for a different length of time: what this run has seen so far, the runbooks each tenant keeps, the reports we save, and small things worth remembering for a while.

Permissions stay in the run's Context, which Session 01 created with the tenant, role and allowed tools and Session 02's tool boundary enforces. None of the four stores grants anything.

Ask

What should the agent do when memory conflicts with what the logs say now?

Show the answer

Keep the conflict as evidence, prefer the verified current source, and never treat memory as an instruction or a permission. Memory is a convenience with a retention policy, not the truth.

Retrieval

Filter by tenant first, then rank

First, what the agent can find. When the model asks runbook_search for evidence, the platform decides which runbooks are candidates before any ranking happens: only those of the run's tenant. So the same query gives different results for different tenants, and every result carries the source ID the answer will cite.

Ask the room

Could we search all runbooks, take the top 10, and then drop the ones from other tenants?

Show the answer

That can return too few results for the tenant and leaks what other tenants have, for example through scores or counts. Apply the boundary to the population you search, or use a retrieval design that enforces it equivalently.

Bounded context

Trim the conversation by complete rounds, never half a round

Second, what the next request carries. Each model request resends the whole conversation, so a long investigation needs a budget. The selector keeps the instruction and the task, then adds whole rounds from the newest backwards while they fit. The full history is still kept for diagnosis; only the next request is smaller.

Ask

Is a shorter prompt always a better prompt?

Show the answer

No. It may leave out the evidence the answer needs. Compare the outcome and the context size on the same cases before adopting a trimming policy; Session 04 gives you the harness to do that.

Saved evidence

Artifacts keep their versions; memory expires

Third, what outlives the request. The message history ends with the run, so anything worth keeping is written somewhere with clear rules: a report as a versioned artifact that refuses a stale overwrite, a small fact as memory that expires. Neither is ever a permission.

Ask

After a version conflict, should the writer simply retry with the latest version number?

Show the answer

Not without reading the newer content first. Retrying blindly turns conflict detection back into an unconditional overwrite.

A real model

The same loop, a real model: only the provider changes

Finally, who reads the request. Every run so far used the deterministic mock. Your Session 01 adapter already speaks the chat-completions format that Groq serves, so connecting a real model is configuration: a provider, a base URL, a model name and a key, read by the platform when it starts a run. Nothing in the loop changes.

What changes is the other side. A real model does things the mock never did, so first you harden the runtime for them. Tuning for each model is normal work; these are the habits we measured when we tested free endpoints in October and again on 2 and 3 November.

Spell out what the model should do. In October one sentence ("Give the final answer as your message text, not as a tool call, and reply with the JSON object only: no Markdown code fence and no other text.") stopped the two answer habits on the model we recommend, qwen/qwen3.8-27b. In November the same model on Groq failed about half of its INC-001 runs, writing runbook_search calls Groq refused. Three changes fixed it. The system prompt now says which tool to call first, with which argument names, when to stop and what the answer must hold. The tool definitions describe what each tool returns and every argument, with an example. And MODEL_REASONING_EFFORT=low lets the model think briefly before each call. With all three, our last six runs completed with correct answers: four of INC-003 and two of INC-001. Two refused calls along the way were retried and succeeded.

Instructions are requests, not guarantees. So the runtime still takes the JSON object out of a fenced or prefaced reply and asks again for a refused tool call, at most twice. openai/gpt-oss-120b, which kept sending its answer as a fake tool call, is not recommended.

Failures get names. Without hardening, a rate limit and a bad key both end as provider_HTTPStatusError. With it, the run says why it stopped, and the console shows the code, so you know whether to wait, fix the key or look at the model's behaviour.

Every model call says who answered. Each model event records the model the endpoint reported, its host and the call's milliseconds. The mock reports itself as model=mock host=offline, which is how the console tells fixture tokens from real ones. A request that fails is a model event too, with its error code, so a failed live run still shows where it went.

def retrieve(query, tenant, limit=2):
    words = set(re.findall(r"[a-z]+", query.lower().replace("_", " ")))
    ranked = [(len(words & set(r["text"].split())), r) for r in RUNBOOKS if r["tenant"] == tenant]
    return [r for score, r in sorted(ranked, key=lambda x: (-x[0], x[1]["source_id"]))
            if score > 0][:limit]
  • The filter is in the comprehension. Other tenants' runbooks never become candidates, so nothing about them can leak through a score.
  • Visible ranking. The score is the count of shared words; ties sort by source ID. You can predict the result before you run it.

def select_context(messages, max_chars=6000):
    """Keep instruction/task and newest COMPLETE tool rounds; never orphan tool IDs."""
    head, rounds, current = messages[:2], [], []
    for message in messages[2:]:
        if message["role"] == "assistant" and current:
            rounds.append(current)
            current = []
        current.append(message)
    if current:
        rounds.append(current)
    retained = []
    for group in reversed(rounds):
        candidate = head + group + retained
        if len(json.dumps(candidate)) > max_chars:
            break
        retained = group + retained
    if len(json.dumps(head)) > max_chars:
        raise ValueError("task_exceeds_context_budget")
    return head + retained
  • A round starts at each assistant message. Its tool results follow it into the same group, so they are kept or dropped together.
  • Newest first. Rounds are added from the end until the next one would break max_chars.
  • Characters, not tokens. A cheap approximation; with a real model, measure the provider's reported usage.

the version check · agent_runtime/context.py · lines 49–62 at lesson-03
def save_artifact(self, tenant, artifact_id, body, expected_version=0):
    self.db.execute("BEGIN IMMEDIATE")
    try:
        version = self.db.execute("SELECT COALESCE(MAX(version),0) FROM artifacts WHERE tenant=? AND id=?",
                                  (tenant, artifact_id)).fetchone()[0]
        if version != expected_version:
            raise ValueError("stale_artifact_version")
        self.db.execute("INSERT INTO artifacts VALUES (?,?,?,?)",
                        (tenant, artifact_id, version+1, json.dumps(body)))
        self.db.execute("COMMIT")
        return version+1
    except BaseException:
        self.db.execute("ROLLBACK")
        raise
  • BEGIN IMMEDIATE takes the write lock before reading the version, so two writers cannot both see version 0.
  • The failure is the feature. A stale writer learns that newer evidence exists instead of erasing it.

take the answer out of the reply · agent_runtime/core.py · lines 98–107 at lesson-03
def final_json(text):
    """The JSON object in a final reply. Real models fence it or write a sentence first despite the
    instruction, so take the first object that parses; a reply with no JSON object fails."""
    decoder = json.JSONDecoder()
    for start in (i for i, ch in enumerate(text) if ch == "{"):
        try:
            return decoder.raw_decode(text, start)[0]
        except ValueError:
            continue
    raise ValueError("invalid_final_answer")
