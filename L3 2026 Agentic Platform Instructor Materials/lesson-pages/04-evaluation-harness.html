Recall

What made the INC-001 report an artifact?

In Session 03 your platform saved the INC-001 investigation report with save_artifact. An artifact is a saved output that people, other agents or later runs rely on, so it carries a name, a version, a tenant and its sources. Today's harness produces artifacts of its own, so start by recalling what that word means.

SAY Session 03 saved the INC-001 report with save_artifact. Recall what made it an artifact rather than memory or message history: other people, agents or later runs rely on it, so it has a name, a version, a tenant and its sources, and a write based on an old version fails with stale_artifact_version. Agentic systems produce several kinds: findings and reports (an investigation report, a root-cause analysis, a review result); plans and proposals (a remediation plan waiting for approval); work products (a patch or pull request, a configuration change, a drafted message, a ticket update); hand-off records between agents (a supervisor's brief, a specialist's result); execution records (runs, traces, tool-call audit, approvals); evaluation artifacts (a case dataset, scored results, a release decision); definitions and configuration (agent definitions, tool manifests, system prompts, model settings); and derived knowledge (a new runbook drafted from a resolved incident). Each needs provenance (which run, agent version, model and sources produced it), a version, an owner and a lifecycle such as draft, proposed, approved, applied, superseded. Writing an artifact is safe; applying it, such as running a remediation plan, is a tool call that goes through approval. Keep this to about five minutes.

The idea

One good run proves nothing: measure the agent on fixed cases, many times

The checks you have passed so far prove that the code behaves as specified: the boundary refuses a tenant argument, a stale write fails. They do not say how well the agent investigates. A real model can answer the same incident differently on two runs, and a change to the prompt, the model or the context can fix one incident and quietly break another. Evaluation is how you find out: run the agent on a fixed set of incidents whose correct outcome is written down in advance, run each one several times, and grade every run against that outcome.

SAY Before adding more agents, we need evidence that complexity helps. Today we build the measuring instrument we will use for the rest of the programme. The current platform can investigate several incidents, including missing or ambiguous evidence. We will define success independently of the agent's preferred sequence of tool calls, run repeated trials and retain a held-out partition. The baseline becomes a reference point for parallel orchestration, provider changes, context policies and capstone tuning.

Grades

Grade the outcome, the evidence and the tool policy separately

A single pass or fail hides why a run failed. The grader asks three questions of every trial and answers each one separately: did the investigation reach the expected status and cause (outcome), is a known cause backed by cited sources (evidence), and did the agent stay away from the write tool while investigating (tool policy). A trial passes only when all three hold.

three checks · agent_runtime/evaluate.py · lines 23–30 at lesson-04
def grade(run, case):
    answer = run.answer or {}
    evidence = answer.get("evidence", [])
    expected_status = "insufficient_evidence" if case["cause"] == "unknown" else "complete"
    return {"outcome": run.status == "completed" and answer.get("cause") == case["cause"]
                        and answer.get("status") == expected_status,
            "evidence": case["cause"] == "unknown" or bool(evidence),
            "tool_policy": all(e.get("name") != "mock_remediate" for e in run.events if e["kind"] == "tool")}

Trials

Run every case several times and keep every row

One run of a real model is a sample, not a result: the same prompt can succeed now and fail on the next call. So the harness runs each case several times, a trial each, and keeps a row per trial with its three checks, tokens, steps, time and cost. The averages summarise the rows; the rows show which case failed, which a single average would hide.

Judge

A model judge is another instrument: check it against people first

Some qualities cannot be checked with code, such as whether a summary is sensible. A model judge is a second model asked to grade the agent's answer against the expected outcome. It is useful and it is fallible, so before trusting it you calibrate it: you give people and the judge the same answers, compare their verdicts, and review every case where they disagree.

paired labels · agent_runtime/evaluate.py · lines 33–37 at lesson-04
def judge_agreement(human_labels, judge_labels):
    if not human_labels or len(human_labels) != len(judge_labels):
        raise ValueError("paired_calibration_labels_required")
    disagreements = [i for i, (a, b) in enumerate(zip(human_labels, judge_labels)) if a != b]
    return {"agreement": 1-len(disagreements)/len(human_labels), "review_indices": disagreements}

The lab's example: people label three answers [True, False, True], the judge says [True, True, True]. Agreement is 0.67, and index 1 is flagged for review: the judge passed an answer a person failed.

The judge receives the agent's answer as data to grade, never as instructions, and its verdict must have the expected shape. Deterministic checks stay in charge of what code can decide, such as a forbidden write or a missing source ID. Today's judge is the interface and its calibration; no live judge runs.
