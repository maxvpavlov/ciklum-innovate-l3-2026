Where we are

Yesterday the model could ask for anything. Today the platform decides what a tool call may do.

Open your Session 01 loop and find its most consequential line: result = await execute(call["name"], call["args"], run.context). Everything the model proposes ends up there. A model can name a tool that does not exist, ask for one this run was never given, send malformed arguments, slip in an argument that changes whose data it reads, receive a result so large it fills the context, or propose an action with real consequences.

Today that line becomes a tool boundary: one executor that every call passes through, whichever way the tool is reached. Then we put the read tools behind the Model Context Protocol (MCP) and show that the boundary does not move.

Terminal or retryable. Every error says whether trying again could help. A permission decision will not change if the agent asks again, so retrying it only burns steps and tokens; at scale, many agents retrying terminal errors become a retry storm. A timeout or a dropped connection may clear, so the executor retries a read once itself and then reports "retryable": true for the caller to decide.

The model sees the error. A denied call still returns an observation, so the model can change course, for example by answering with the evidence it has. Seeing the error never changes the decision.

Ask the room

Can a correct JSON Schema make a tool safe by itself?

Show the answer

No. A perfectly well-formed request can still be unauthorized or harmful. The schema checks shape; the run's allowed tools check authority; approval and the effect ledger control consequences. They are separate checks, and the order matters.

Context supplies authority; the schema supplies shape. The executor reads the run's Context, which the platform built in Session 01, and never anything the model wrote. The model cannot widen its own permissions by naming a tool, and it cannot pick another tenant through a legitimate tool, because the log schema forbids extra properties and the tenant comes from Context.

The output limit protects the conversation. Every observation is appended to the messages and sent back on every later turn. One unexpectedly large result could consume the whole token budget, so the executor refuses results above output_limit characters (6,000 by default).

Restart

The process restarts and the same approved call arrives again, as it would when a run resumes after a crash.

{"ok": true, "simulated": true, "action": "rollback", "incident_id": "INC-001", "replayed": true}

The ledger already has the key, so the stored result comes back. One effect in the table, not two.

Why one transaction. If the effect and the "done" record were written separately, a crash between them would leave an effect with no record, and the retry would do it again. Writing both in one transaction means either both exist or neither does.

Where the guarantee ends. This is a local SQLite demonstration. For a real external API, a flag in your own database cannot make a remote operation happen exactly once: your process can crash after the remote call succeeds and before you record it. The receiver must support an idempotency key, or you need a reconciliation step that checks what actually happened. Session 05 makes the approval pause itself durable, with a run status of waiting_approval and an operator decision.

Ask

Why is checking a dictionary of "already done" actions before a remote write not enough?

Show the answer

The process can crash between the remote write and recording success, and an in-memory dictionary does not survive a restart at all. You need a durable record committed with the effect, or a receiver-side idempotency key, or reconciliation.

The protocol

MCP standardizes how tools are found and reached. It does not decide who may use them.

MCP in brief

The Model Context Protocol (MCP) is an open standard, introduced by Anthropic in November 2024, for connecting AI applications to tools and data. Before it, every application wrote its own adapter for every tool. With MCP, a tool provider writes one server, and any MCP-capable application, such as a coding agent, a chat app or our platform, can discover and call it the same way. The specification compares it to a USB-C port for AI applications.

MCP standardizes the connection only. It says how to list a server's tools and call them; it says nothing about which tools a given agent should be allowed to use. That decision stays with the platform, and it is what today's executor makes.

What a server offers

Tools the model may ask to run, resources the application can read, and reusable prompts. We use two tools and one resource.

How they talk

JSON-RPC 2.0 messages, such as tools/list and tools/call, each with a schema the specification defines.

Over which transport

stdio, where the application starts the server as a child process, or Streamable HTTP for a remote server. We use stdio.

In what order

initialize negotiates the protocol version and capabilities; then the client lists what the server offers and calls it.

Host

The application the user works with: here, your platform process. It decides which servers to start, and with which command.

Client

One connection to one server, inside the host. It negotiates the protocol version, lists what the server offers and calls it.

Server

A program that offers capabilities. Ours wraps Session 01's two readers, so the evidence is identical.

Tool vs resource

A tool is an operation with parameters that the model may ask to run. A resource is addressable content, such as incident://runbooks, that the application reads when it chooses.

What discovery actually returns

How the platform hands tools to an agent

Follow the tools from left to right. Each stage narrows what the next one sees, and the model only ever receives the last list.

The server is not your policy. Call the server directly with log_lookup {"incident_id": "INC-001", "tenant": "locomotive"} and it does not complain: the extra argument is ignored and Astro's record comes back, because the tenant was fixed when the server started. Through your executor the same request fails with invalid_arguments. The executor validates against the platform's own contract, so a server that is lax, changes its schema or advertises something new cannot widen what a run may do.

Trust boundary of this demo. With stdio, identity is the process boundary: the trusted launcher sets INCIDENT_TENANT, and model output can never choose the command. A remotely deployed HTTP MCP server would need real authentication, token validation and authorization. This course does not exercise remote MCP OAuth, and we do not claim it.

Launching one MCP server per client is deliberately simple. Session 09 replaces it with a central tool gateway that shares upstream sessions, applies one policy, audits every call and pins tool definitions, so that a changed definition is caught instead of silently trusted.

the three checks · agent_runtime/tools.py · lines 34–43 at lesson-02
async def execute(self, name, args, context):
    schemas = {s["function"]["name"]: s["function"]["parameters"] for s in self.schemas}
    if name not in schemas:
        return {"ok": False, "error": "unknown_tool", "retryable": False}
    if name not in context.allowed:
        return {"ok": False, "error": "permission_denied", "retryable": False}
    try:
        validate(args, schemas[name])
    except ValidationError:
        return {"ok": False, "error": "invalid_arguments", "retryable": False}

  • Order. Existence, then permission, then shape. A read-only run asking for mock_remediate gets permission_denied without its arguments ever being examined.
  • One timeout, one retry. A read that times out or loses its connection is tried once more after 10 ms; a second failure becomes tool_unavailable with "retryable": true. Nothing else is retried.
  • Size. The serialized result must fit output_limit; otherwise the observation is the error, not the data.

Because asking again cannot change it: the decision comes from the run's Context, not from timing or luck. Marking it terminal stops the agent, and any caller, from wasting steps or creating a retry storm.

def action_key(name, args, context):
    payload = [context.tenant, context.run_id, name, args]
    return hashlib.sha256(json.dumps(payload, sort_keys=True).encode()).hexdigest()

def make_server(tenant="astro"):
    server = MCPServer("incident-tools")
    context = Context(tenant=tenant)

    @server.tool()
    async def log_lookup(incident_id: str) -> dict:
        """Read diagnostic incident evidence in the launcher's tenant."""
        return await simple_tools("log_lookup", {"incident_id": incident_id}, context)

    @server.tool()
    async def runbook_search(query: str) -> dict:
        """Find relevant runbook evidence in the launcher's tenant."""
        return await simple_tools("runbook_search", {"query": query}, context)

    @server.resource("incident://runbooks")
    def runbooks() -> str:
        return json.dumps([r for r in RUNBOOKS if r["tenant"] == tenant])

    return server

class MCPReadAdapter:
    def __init__(self, client):
        self.client = client

    async def __call__(self, name, args, context):
        # Use behind ToolExecutor, which validates and authorizes every dispatch.
        result = await self.client.call_tool(name, args)
        if result.is_error:
            return {"ok": False, "error": "mcp_tool_error"}
        if result.structured_content is not None:
            return result.structured_content
        return json.loads(next(c.text for c in result.content if c.type == "text"))

  • Nothing here grants anything. The adapter sits behind the executor, which has already checked the call.
